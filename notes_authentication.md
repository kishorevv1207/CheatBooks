```text
      ↓

      ↓
```

If it matches:

```text

```

If it doesn't:

```text
❌ Invalid username or password
```

```json
  "role": "customer",

  "exp": 1790003600
```

# 5. Where is the JWT saved?

This is where things become important.

There are **two different things** to think about:

### Access token

The JWT access token is typically kept by the **client** so it can send it with subsequent requests.

For example:

```text

   ↓

```

Then:

```http
GET /accounts

```

The server can validate the JWT without necessarily looking up a server-side session for every request.

### Server side

A JWT is often **not stored in the database at all**.

The server can verify it using its signing key:

```text
JWT
 ↓
Verify signature
 ↓
Check expiration
 ↓
Read user ID / claims
 ↓
Allow or deny request
```

That's one reason JWTs are commonly used for stateless authentication.

# 7. Access Token vs Refresh Token

This is especially important when learning JWT.


```text

15 minutes

   ↓
Longer lifetime
```

When the access token expires:

```text

  ↓
Refresh token
  ↓
Authentication server
  ↓
New access token
```

A refresh token is generally handled more carefully and may be stored/revoked server-side depending on the architecture.

## What is a Password Hash?

A **password hash** is the output produced when a password is processed through a **one-way cryptographic hashing algorithm**.

Instead of storing the user's actual password in the database, the application stores its hash.

### Simple Example

Suppose a user creates an account:

```text
Username: kishore123
Password: MyPassword@123
```

During registration:

```text
MyPassword@123
       ↓
Password Hashing Algorithm (bcrypt)
       ↓
$2b$12$LQv3c1yqBWVHxkd0LHAkCO...
       ↓
Stored in Database
```

The database stores something like:

| Username   | Password Hash                      |
| ---------- | ---------------------------------- |
| kishore123 | `$2b$12$LQv3c1yqBWVHxkd0LHAkCO...` |

**The original password is not stored.**

---

### How Login Verification Works

When the user logs in again:

```text
User enters password
       ↓
"MyPassword@123"
       ↓
Backend retrieves stored hash
       ↓
Password verification function
       ↓
Match?
```

If the password is correct:

```text
✅ Login successful
```

If incorrect:

```text
❌ Invalid username or password
```

### Important: It Does Not Simply Hash and Compare Two Strings

With algorithms such as **bcrypt**, the stored hash contains information needed for verification, including the salt and cost factor.

The application uses a verification function:

```python
import bcrypt

stored_hash = bcrypt.hashpw(
    b"MyPassword@123",
    bcrypt.gensalt()
)

# Later, during login
is_valid = bcrypt.checkpw(
    b"MyPassword@123",
    stored_hash
)

print(is_valid)  # True
```

The actual application would store `stored_hash` in the database and retrieve it during login.

---

### Why Not Store Plaintext Passwords?

**Plaintext storage:**

```text
Database:
Username: kishore123
Password: MyPassword@123
```

If the database is leaked, attackers may directly see the passwords.

**Hashed storage:**

```text
Database:
Username: kishore123
Password Hash: $2b$12$...
```

The attacker does not directly get the original password from the stored hash.

> **Hashing is not encryption.** Encryption is designed to be reversible using a key. Password hashing is designed to be one-way and difficult to reverse.

### Hashing vs Encryption

| Feature             | Hashing                              | Encryption                                                             |
| ------------------- | ------------------------------------ | ---------------------------------------------------------------------- |
| Purpose             | Protect passwords / verify integrity | Protect data confidentiality                                           |
| Reversible?         | Designed to be one-way               | Yes, with the correct key                                              |
| Used for passwords? | ✅ Yes                                | ❌ Passwords should generally not be stored using reversible encryption |
| Example             | bcrypt, Argon2, scrypt               | AES                                                                    |

### What is Salt?

A **salt** is a random value added during password hashing.

```text
Password + Random Salt
          ↓
      Hashing
          ↓
      Password Hash
```

Salts help ensure that even if two users choose the same password, their stored hashes can be different.

For example:

```text
User A → "hello123" → Hash A
User B → "hello123" → Hash B
```

With a properly generated random salt, **Hash A and Hash B will normally be different**.

### Interview Answer

> "A password hash is a one-way representation of a password generated using a password-hashing algorithm such as bcrypt, Argon2, or scrypt. We store the hash instead of the plaintext password. During login, the entered password is verified against the stored hash. Hashing is different from encryption because it is designed to be one-way."

**Simple memory trick:**
**Password → Hash → Store → Verify during login.**

## 1. Where is the hashed password stored?

The hashed password is stored in the **user database**, usually in a dedicated column in a users table.

For example, a banking application might have a database like:

**Database: `banking_db`**

**Table: `users`**

| id    | username   | password_hash        | status |
| ----- | ---------- | -------------------- | ------ |
| 10245 | kishore123 | `$2b$12$LQv3c1yq...` | ACTIVE |
| 10246 | user456    | `$2b$12$AbC9x7...`   | ACTIVE |

The database could be **PostgreSQL, MySQL, SQL Server, Oracle**, etc. The specific database depends on the application's architecture.

**Important:** The password hash is stored in the database, not inside the JWT.

---

## 2. User enters the password

Suppose the user enters:

```text
Username: kishore123
Password: MyPassword@123
```

The frontend sends the credentials to the backend:

```http
POST /login
Content-Type: application/json
```

```json
{
  "username": "kishore123",
  "password": "MyPassword@123"
}
```

But because the URL uses **HTTPS**, the communication is protected by TLS.

---

## 3. Where does HTTPS encrypt the password?

HTTPS uses **TLS encryption** to protect the HTTP request while it travels between the client and server.

```text
Browser / Mobile App
        │
        │ Plaintext exists here
        ▼
   TLS Encryption
        │
        ▼
Encrypted network traffic
        │
        ▼
      Internet
```

### Important clarification

HTTPS does **not necessarily encrypt the password inside your application before the request is created**.

The application creates an HTTP request containing the password, and **TLS protects that request during transmission**.

So conceptually:

```text
Application data
      ↓
HTTP request
      ↓
TLS encryption
      ↓
Network
```

---

## 4. Where does HTTPS decrypt the password?

The TLS-encrypted traffic is decrypted at the **TLS termination point**.

This may be:

* A **load balancer**
* A **reverse proxy** such as Nginx
* An **API gateway**
* Or the **application server itself**

For example:

```text
Mobile App
    │
    │ HTTPS encrypted
    ▼
Load Balancer / API Gateway
    │
    │ TLS decrypted
    ▼
Banking Backend
```

Or, in a simpler architecture:

```text
Mobile App
    │
    │ HTTPS encrypted
    ▼
Banking Backend
    │
    │ TLS decrypted
    ▼
Application code
```

After TLS decryption, the backend can access the HTTP request data.

```json
{
  "username": "kishore123",
  "password": "MyPassword@123"
}
```

**HTTPS decryption does not mean the password is decrypted into a hash.** It only makes the original request data available to the receiving application.

---

## 5. Where does password verification happen?

Password verification happens in the **backend authentication service**, not in HTTPS and not normally inside the database.

The flow is:

```text
Backend receives username + password
                ↓
Query database using username
                ↓
Retrieve stored password hash
                ↓
Password verification library
                ↓
Compare entered password against stored hash
                ↓
True / False
```

### Example

The backend retrieves:

```text
Entered password:
MyPassword@123

Stored hash:
$2b$12$LQv3c1yqBWVHxkd0LHAkCO...
```

Then it calls a password verification function, such as:

```python
bcrypt.checkpw(entered_password, stored_hash)
```

The library checks whether the entered password corresponds to the stored hash.

```text
Match → Login successful
No match → Login failed
```

### Important distinction

The backend does **not normally decrypt the stored hash** to get the original password.

Instead:

> **The entered password is verified against the stored hash using the password-hashing algorithm.**

---

## 6. Does the database receive the original password?

Usually, **no**.

The typical flow is:

```text
Client
  │
  │ Original password inside HTTPS request
  ▼
TLS termination
  │
  ▼
Backend authentication service
  │
  ├── Receives original password temporarily in memory
  │
  ├── Retrieves password hash from database
  │
  └── Verifies password
```

The backend needs access to the entered password to verify it. But it should **not store the plaintext password** in the database, logs, or application files.

The database typically stores only:

```text
password_hash
```

## One Important Correction About "Encrypted Password"

You said:

> "When the user enters the password it was encrypted by HTTPS and where it decrypts and checks with hashed passwords?"

The accurate version is:

| Stage                | What happens                                       |
| -------------------- | -------------------------------------------------- |
| User enters password | Original password exists in the client application |
| HTTPS transmission   | TLS encrypts the HTTP request                      |
| TLS termination      | Request is decrypted at the gateway/server         |
| Backend              | Receives the entered password                      |
| Database             | Returns the stored password hash                   |
| Password library     | Verifies entered password against hash             |
| Success              | Backend may generate an access token               |

### Final Interview Answer

> "The hashed password is stored in the users table of the database. When a user logs in, the password is sent to the backend over HTTPS, where TLS decrypts the request at the server or TLS termination point. The backend retrieves the stored password hash from the database and uses a password-hashing library such as bcrypt or Argon2 to verify the entered password against that hash. If verification succeeds, the backend can generate an access token, such as a JWT."

**Remember:**

**HTTPS protects the password in transit. Hashing protects the password at rest.**
